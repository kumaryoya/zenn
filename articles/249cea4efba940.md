## AWS CDK とは

[AWS CDK（Cloud Development Kit）](https://docs.aws.amazon.com/ja_jp/cdk/v2/guide/home.html) は、TypeScript や Python などの一般的なプログラミング言語でクラウドリソースを定義できる IaC（Infrastructure as Code）ツールです。

書いたコードは CloudFormation テンプレートに変換され、CloudFormation 経由でデプロイされます。

https://docs.aws.amazon.com/ja_jp/cdk/v2/guide/home.html

## なぜインフラもコードで管理すべきなのか

IaC のメリットとしては「再現性」や「レビューできること」がよく挙げられますが、AI と一緒に開発する時代には、もう 1 つ大きな理由があると感じています。

それは、**AI がインフラを把握できるようになる**ことです。

### AI は「見えるもの」しか理解できない

Claude Code のような AI エージェントは、リポジトリ内のファイルを読んでプロジェクトを理解します。

アプリのコードがどれだけ整っていても、インフラがマネジメントコンソール上にしか存在しなければ、AI は推測で答えるしかありません。

インフラをコードにしておけば、AI はアプリのコードと同じように読み、理解してくれます。

### アプリとインフラをつなげて理解できる

実際の不具合や改修は、アプリとインフラの境目で起きることが少なくありません。

たとえば「この環境変数はどこで設定されているのか」「このバッチはどのタスク定義で、いつ動いているのか」といった疑問は、アプリとインフラの両方を見ないと答えられません。

両方がコードになっていれば、AI が横断的に調べて答えてくれます。

### 変更の経緯を AI も追える

インフラの変更がプルリクエスト経由になることで、Git の履歴に「いつ・誰が・なぜ変えたのか」が残ります。

人間がレビューできるのはもちろん、AI も `git log` をたどって経緯を把握できるようになります。

## Terraform ではなく CDK にした理由

IaC ツールとしては Terraform も有力な選択肢です。

マルチクラウドに対応していることや、AWS 以外のサービス（GitHub、Datadog など）もまとめて管理できることは、Terraform の大きな強みだと思います。

それでも今回 CDK を選んだ一番の理由は、**会社で既に CDK を採用していたから**です。

社内の別サービスのインフラは CDK で管理されており、既存のコードや知見をそのまま参考にできました。

それに加えて、CDK には以下のようなメリットがあると感じています。

### メリット① アプリと同じ言語で書ける

CDK は TypeScript で書けるため、エディタの補完や型チェックがそのまま効きます。

プロパティ名の打ち間違いや型の誤りは、デプロイ前にコンパイルエラーとして検出されます。

これは AI にとっても同じで、AI が書いたコードに誤りがあっても `tsc` のエラーを見て自分で修正してくれます。

また、ループや条件分岐、関数による共通化も普通のプログラミングと同じように書けます。

```ts
// 環境ごとに異なる設定を、普通の TypeScript で書ける
const isProduction = envType === 'production'

const taskDefinition = new ecs.FargateTaskDefinition(this, 'TaskDefinition', {
  cpu: isProduction ? 1024 : 256,
  memoryLimitMiB: isProduction ? 2048 : 512,
})
```

### メリット② 少ない記述でベストプラクティスに沿ったリソースを作れる

CDK には L2 Construct と呼ばれる抽象化されたクラスが用意されており、安全な初期値が最初から設定されています。

特に便利なのが、IAM ポリシーを自動で作ってくれる `grant` 系のメソッドです。

```ts
// タスクロールに、このバケットの読み取り権限だけを付与する
bucket.grantRead(taskDefinition.taskRole)
```

この 1 行で、必要最小限の権限を持つ IAM ポリシーが自動で作られます。

手作業で IAM ポリシーを書いていると、つい `s3:*` のような広すぎる権限を付けてしまいがちですが、CDK ならそういった事故も防げます。

### メリット③ 状態管理を CloudFormation に任せられる

Terraform では、どのリソースを管理しているかを記録する state ファイル（tfstate）を、自分で管理する必要があります。

チームで使う場合は、S3 などに state ファイルを置き、同時に更新されないようにロックする仕組みも用意しなければなりません。

一方 CDK は、状態管理を CloudFormation に任せられるため、こうした準備が不要です。

デプロイに失敗したときも、CloudFormation が自動でロールバックしてくれます。

## 既存のインフラを CDK に落とし込む

ここからは、実際に既存のインフラを CDK に落とし込んだ手順です。

進め方は、AWS 公式の [CDK のベストプラクティス](https://docs.aws.amazon.com/ja_jp/cdk/v2/guide/best-practices.html) に合わせました。

https://docs.aws.amazon.com/ja_jp/cdk/v2/guide/best-practices.html

### 取り込み方法の選択肢

既存のリソースを CDK の管理下に置く方法は、大きく分けて以下の 3 つがあります。

| 方法 | 内容 |
| --- | --- |
| `cdk migrate` | 既存のリソースをスキャンし、CDK のコードを自動生成する |
| `cdk import` | 自分で書いた CDK のコードに、既存のリソースを紐付ける |
| 作り直し | CDK で新しくリソースを作り、既存のリソースから切り替える |

### `cdk migrate` を使わなかった理由

一番手軽なのは `cdk migrate` ですが、今回は使いませんでした。

[公式ドキュメント](https://docs.aws.amazon.com/ja_jp/cdk/v2/guide/migrate.html) にある通り、`cdk migrate` には以下の制約があるためです。

- プレビュー版の機能である
- 生成されるのは L1 Construct（CloudFormation をほぼそのまま書き写したコード）のみ
- すべてのリソースが 1 つのスタックにまとめられる

今回の目的は「AI にインフラを把握させること」です。

CloudFormation を書き写しただけの長大なコードでは、人間にも AI にも読みづらく、目的と逆行してしまいます。

そのため、L2 Construct を使って自分でコードを書き、そこに既存のリソースを紐付ける方針にしました。

### ステートフルかステートレスかで方針を分ける

[`cdk import` の公式ドキュメント](https://docs.aws.amazon.com/ja_jp/cdk/v2/guide/ref-cli-cmd-import.html) では、以下のように説明されています。

- IAM ロールや Lambda 関数、EventBridge のルールなどは、新しく作り直しても問題ないことが多い
- S3 バケットやデータベースのような、データを持つ（ステートフルな）リソースは、作り直すとサービスに影響が出る

そこで、リソースを以下の 3 つに分類して進めました。

| 分類 | 方針 | 例 |
| --- | --- | --- |
| データを持つリソース | `cdk import` で取り込む | RDS / S3 |
| データを持たないリソース | CDK で作り直して切り替える | ECS サービス / タスク定義 / Lambda / IAM ロール / EventBridge |
| 構造が複雑な基盤リソース | 当面は参照のみ（`fromLookup`） | VPC / サブネット |

<!-- TODO: 実際の分類に合わせて修正 -->

VPC は取り込むこともできますが、L2 の `Vpc` Construct はサブネットやルートテーブルを独自のルールで生成するため、手作業で作った構成と一致させるのが大変です。

まずは `Vpc.fromLookup` で既存の VPC を参照するだけにして、管理対象に含めるかどうかは後から判断することにしました。

```ts
// 既存の VPC を参照する（CDK の管理対象にはならない）
const vpc = ec2.Vpc.fromLookup(this, 'Vpc', { vpcId: 'vpc-xxxxxxxx' })
```

### スタックを分ける

ベストプラクティスでは、ステートフルなリソースをステートレスなリソースとは別のスタックに置き、終了保護を有効にすることが推奨されています。

```ts
const app = new cdk.App()

// データを持つリソース（削除されると困るので終了保護を有効にする）
const statefulStack = new StatefulStack(app, 'StatefulStack', {
  terminationProtection: true,
})

// データを持たないリソース（作り直しても問題ない）
new StatelessStack(app, 'StatelessStack', {
  bucket: statefulStack.bucket,
})
```

こうしておけば、ステートレスなスタックは気軽に作り直せる一方で、データを持つリソースを誤って消してしまう事故を防げます。

### CDK のコードも AI に書いてもらう

既存のリソースと同じ設定の CDK のコードを、ゼロから手で書くのはかなり大変です。

そこで、CDK のコードを書く作業自体も Claude Code に手伝ってもらいました。

進め方は以下の通りです。

1. Claude Code に AWS CLI で既存のリソースの設定を調べてもらう
2. 調べた設定をもとに、L2 Construct を使った CDK のコードを書いてもらう
3. 書かれたコードを人間がレビューし、マネジメントコンソールの設定と突き合わせる

ただし、AI に任せる際は以下の点に注意しました。

- **AWS CLI は読み取り専用の権限で実行する**
  - 調査の途中で、AI が誤ってリソースを変更・削除してしまう事故を防ぐためです
- **AI が書いたコードをそのまま信用しない**
  - 手作業で作った構成には、一般的なパターンから外れた設定が含まれていることがあります
  - AI はよくある書き方に寄せがちなので、既存の設定が上書きされていないかを必ず確認しました
- **デプロイの前に必ず `cdk diff` で差分を確認する**
  - 意図しないリソースの作り直しや削除が含まれていないかを、人間の目で確認します

### ステートフルなリソースを `cdk import` で取り込む

S3 バケットを例に、`cdk import` の流れを紹介します。

まず、`cdk diff` で未反映の変更がないことを確認します。

`cdk import` では、取り込むリソースの追加以外の変更が許されていないためです。

```bash
npx cdk diff StatefulStack
```

次に、既存のバケットと**同じ設定**になるように CDK のコードを書きます。

```ts
export class StatefulStack extends Stack {
  public readonly bucket: s3.IBucket

  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props)

    this.bucket = new s3.Bucket(this, 'UploadBucket', {
      bucketName: 'example-upload-bucket', // 既存のバケット名
      encryption: s3.BucketEncryption.S3_MANAGED,
      blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
      removalPolicy: RemovalPolicy.RETAIN, // スタックを消してもバケットは残す
    })
  }
}
```

ここで設定が既存のリソースとずれていると、次回のデプロイで意図しない変更が入ってしまいます。

暗号化やライフサイクルルール、バケットポリシーなど、Claude Code が AWS CLI で調べた設定を、マネジメントコンソールとも 1 つずつ突き合わせて確認しました。

コードが書けたら `cdk import` を実行します。

```bash
npx cdk import StatefulStack
```

取り込むリソースの実際の名前を聞かれるので、既存のバケット名を入力すれば取り込みが始まります。

最後に、CloudFormation のドリフト検出を実行し、コードと実際のリソースの設定に差分がないかを確認します。

`cdk import` は、書いた設定が既存のリソースと一致しているかまではチェックしてくれないためです。

データを持たないリソースは、CDK で新しく作り、動作を確認してから切り替えました。

作り直しなので、マネジメントコンソールでの設定を完全に再現する必要はなく、このタイミングで不要な設定や広すぎる権限を整理できたのも良かった点です。

### 注意したポイント

ベストプラクティスを読んで、特に注意したのは以下の点です。

- **ステートフルなリソースの論理 ID を変えない**
  - CDK では、Construct の ID やツリー上の位置から論理 ID が決まります
  - リファクタリングで論理 ID が変わると、リソースが作り直されてしまいます
- **削除ポリシーを明示する**
  - データを持つリソースには `RemovalPolicy.RETAIN` を指定し、スタックから外れてもリソースが残るようにしました
- **L2 Construct が裏で作るリソースに注意する**
  - L2 Construct は、付随するリソース（セキュリティグループやポリシーなど）を自動で作ることがあります
  - `cdk import` ではリソースの追加以外の変更が許されないため、取り込むときは `cdk diff` で何が作られるかを事前に確認しました
- **`cdk.context.json` をコミットする**
  - `fromLookup` の結果はここにキャッシュされます
  - コミットしておかないと、実行するタイミングによって結果が変わる可能性があります

## CDK 化して AI の回答はどう変わったか

CDK 化の前後で、Claude Code に同じ質問をしたときの回答を比べてみます。

:::message
CDK 化前の回答は記録を残していなかったため、以下はどちらも当時のやり取りをもとに再現したイメージです。
:::

### 例① バッチの実行時刻とリソース

> 集計バッチは何時に動いていて、CPU とメモリはいくつ割り当てられている？

**CDK 化前**

```
リポジトリ内に、バッチのスケジュールやタスクのリソース設定に関する記述は見つかりませんでした。

一般的には cron や EventBridge で定期実行されていることが多いです。
AWS マネジメントコンソールの EventBridge や ECS の画面で確認してください。
```

リポジトリにないものは答えられないので、一般論と「コンソールを見てください」で終わってしまいます。

**CDK 化後**

```
StatelessStack の定義によると、集計バッチは以下の設定です。

- 実行時刻: 毎日 3:00（JST）
  - EventBridge のルールで cron(0 18 * * ? *) を指定（UTC）
- CPU / メモリ
  - production: 1024（1 vCPU）/ 2048 MiB
  - それ以外: 256（0.25 vCPU）/ 512 MiB
  - envType によって切り替えています
```

スタックのコードを読んで、UTC と JST の変換や環境ごとの違いまで含めて答えてくれるようになりました。

### 例② 権限まわりのエラー

> アプリから S3 へのアップロードで AccessDenied が出る。原因は？

**CDK 化前**

```
考えられる原因は以下の通りです。

1. IAM ロールに s3:PutObject の権限がない
2. バケットポリシーで拒否されている
3. KMS キーの権限が不足している

IAM コンソールで、タスクロールに付与されているポリシーを確認してください。
```

間違ってはいませんが、どれが原因かを切り分けるのは人間の仕事のままです。

**CDK 化後**

```
StatelessStack で、タスクロールには bucket.grantRead() で読み取り権限だけが付与されています。
そのため、s3:PutObject が許可されておらず AccessDenied になっています。

grantRead を grantReadWrite に変更すれば解消できます。修正しますか？
```

原因を特定するだけでなく、そのままコードの修正まで進めてくれるようになりました。

インフラの変更もアプリと同じくプルリクエストでレビューできるので、AI に修正を任せても安心です。

### 変わったこと

2 つの例に共通しているのは、AI の回答が **「一般論」から「このプロジェクトの事実」に変わった**ことです。

これまでは、AI の回答をもとに人間がマネジメントコンソールを確認しに行く必要がありました。

CDK 化してからは、AI がアプリとインフラの両方を読んで、原因の特定から修正まで一気に進めてくれます。

また、CDK のリポジトリにも `CLAUDE.md` を置いておくと、スタックの構成や依存関係を毎回ゼロから調べずに済むので、さらに回答の精度が上がります。

## まとめ

AI にコードを書かせる時代だからこそ、アプリだけでなくインフラもコードで管理しておく価値が高まっていると感じました。

AI は、リポジトリにあるものしか理解できません。

インフラをコードにすることは、人間のためだけでなく、AI にプロジェクト全体を把握してもらうための準備でもあります。

既存のインフラを取り込む際は、データを持つリソースは `cdk import`、データを持たないリソースは作り直し、と分けて考えると、安全に進められます。

また、CDK のコードを書く作業自体も AI に手伝ってもらえるので、手作業で作ったインフラを CDK 化するハードルは以前よりずっと下がっています。
