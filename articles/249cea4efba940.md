## はじめに

私は普段から Claude Code を使って開発しており、リポジトリにあるアプリのコードを読んで、既存の実装に沿ったコードを書いてくれるので、とても助かっています。

しかし、個人開発しているアプリでは、AI が書くコードが、実際のインフラ構成に合っていないことがありました。

例えば、タスクに設定されていない環境変数を前提にしたコードや、権限のない S3 バケットに書き込むコードを書いてしまい、デプロイしてから初めて動かないことに気づく、といった具合です。

考えてみれば当然で、このアプリのインフラはマネジメントコンソール（以下、マネコン）から手作業で作っていたため、AI からは一切見えません。

そのため、インフラ構成を知らないまま、「よくある構成」を想像してアプリのコードを書くしかありません。

そこで、業務で CDK を使っている経験を活かして、個人開発のアプリのインフラを AWS CDK に落とし込み、アプリと同じようにコードで管理するようにしました。

CDK 化してからは、AI が環境変数の名前や IAM の権限まで、実際のインフラ構成に合わせてコードを書いてくれるようになりました。

本記事では、その過程と、CDK を選んだ理由、そして CDK 化の前後で AI が書くコードがどう変わったかをご紹介します。

少しでも皆様の参考になりますと幸いです。

## 前提

今回対象にしたのは、個人開発で運用しているアプリのインフラです。

インフラは、すべてマネコンから手作業で構築していました。

- **ネットワーク**：VPC、ALB、WAF
- **アプリケーション**：ECS（Fargate）
- **データベース・ストレージ**：RDS、S3
- **定期実行**：EventBridge
- **権限**：IAM ロール

また、本番環境のほかに、検証用の環境も用意しています。

## AWS CDK とは

AWS CDK（Cloud Development Kit）とは、AWS が提供する IaC（Infrastructure as Code）ツールで、TypeScript や Python などの一般的なプログラミング言語で AWS のリソースを定義できます。

書いたコードは CloudFormation テンプレートに変換され、CloudFormation 経由でデプロイされます。

https://docs.aws.amazon.com/ja_jp/cdk/v2/guide/home.html

## なぜインフラもコードで管理するのか

IaC のメリットとしては、再現性やレビューのしやすさがよく挙げられます。

それに加えて、AI と一緒に開発する上では、AI がインフラ構成を把握できるようになることも大きなメリットだと思います。

Claude Code は、リポジトリ内のファイルを読んでプロジェクトを理解します。

そのため、インフラもコードとしてリポジトリに置いておけば、アプリのコードと同じように読んでくれます。

また、インフラの変更もプルリクエスト経由になるため、Git の履歴に変更の経緯が残り、後から確認できるようになります。

## CDK を選んだ理由

IaC ツールとしては Terraform も有力な選択肢です。

マルチクラウドに対応していることや、AWS 以外のサービス（GitHub、Datadog など）もまとめて管理できることは、Terraform の大きな強みだと思います。

それでも今回 CDK を選んだ一番の理由は、業務で CDK を使っているからです。

弊社では自社サービスのインフラを CDK で管理しており、私も日頃から CDK のコードを読み書きしています。

そのため、個人開発でも CDK を使えば、業務で得た知識をそのまま活かせると考えました。

また、CDK には以下のようなメリットがあると思います。

### メリット① 使い慣れたプログラミング言語で書ける

CDK は TypeScript や Python などで書くことができ、今回は業務でも使っている TypeScript を選びました。

そのため、エディタの補完や型チェックがそのまま効きます。

プロパティ名の打ち間違いや型の誤りは、デプロイ前にコンパイルエラーとして検出することができます。

これは AI にとっても同じで、AI が書いたコードに誤りがあっても `tsc` のエラーを見て自分で修正してくれます。

また、ループや条件分岐、関数による共通化も普通のプログラミングと同じように書けます。

```ts
// 環境ごとに異なる設定を、普通の TypeScript で書ける
const isProduction = envType === 'production'

const taskDefinition = new ecs.FargateTaskDefinition(this, 'TaskDefinition', {
  cpu: isProduction ? 1024 : 256,
  memoryLimitMiB: isProduction ? 2048 : 512,
})
```

### メリット② 少ない記述でベストプラクティスに沿ったリソースを作れる

CDK には L2 Construct と呼ばれる抽象化されたクラスが用意されており、安全な初期値が最初から設定されています。

特に便利なのが、IAM ポリシーを自動で作ってくれる `grant` 系のメソッドです。

```ts
// タスクロールに、このバケットの読み取り権限だけを付与する
bucket.grantRead(taskDefinition.taskRole)
```

この 1 行で、必要最小限の権限を持つ IAM ポリシーが自動で作られます。

手作業で IAM ポリシーを書いていると、必要以上に広い権限を付けてしまうこともありますが、`grant` 系のメソッドを使えば、そういった心配も少なくなります。

## 既存のインフラを CDK に落とし込む

ここからは、実際に既存のインフラを CDK に落とし込んだ手順をご紹介します。

進め方は、AWS 公式の CDK のベストプラクティスに合わせました。

https://docs.aws.amazon.com/ja_jp/cdk/v2/guide/best-practices.html

### 取り込み方法の選択肢

既存のリソースを CDK の管理下に置く方法は、大きく分けて以下の 3 つがあります。

| 方法 | 内容 |
| --- | --- |
| `cdk migrate` | 既存のリソースをスキャンし、CDK のコードを自動生成する |
| `cdk import` | 自分で書いた CDK のコードに、既存のリソースを紐付ける |
| 作り直し | CDK で新しくリソースを作り、既存のリソースから切り替える |

### `cdk migrate` を使わなかった理由

一番手軽なのは `cdk migrate` ですが、今回は使いませんでした。

[公式ドキュメント](https://docs.aws.amazon.com/ja_jp/cdk/v2/guide/migrate.html) にある通り、`cdk migrate` には以下の制約があるためです。

- プレビュー版の機能である
- 生成されるのは L1 Construct（CloudFormation をほぼそのまま書き写したコード）のみ
- すべてのリソースが 1 つのスタックにまとめられる

CloudFormation をほぼそのまま書き写したコードは長くなりがちで、人間にも AI にも読みづらいと思います。

今回は AI にインフラ構成を把握させることが目的だったので、L2 Construct を使ってコードを書き、そこに既存のリソースを紐付けることにしました。

### 既存のリソースはすべて `cdk import` で取り込む

`cdk import` の [公式ドキュメント](https://docs.aws.amazon.com/ja_jp/cdk/v2/guide/ref-cli-cmd-import.html) では、以下のように説明されています。

- S3 バケットやデータベースのような、データを持つ（ステートフルな）リソースは、作り直すとサービスに影響が出る
- IAM ロールや EventBridge のルールなどは、新しく作り直しても問題ないことが多い

しかし、今回はデータを持たないリソースも含めて、既存のリソースはすべて `cdk import` で取り込みました。

作り直す場合は、新しいリソースを作ってから既存のリソースと切り替える作業が必要になり、その間にサービスへ影響が出るリスクがあります。

すべて `cdk import` で取り込めば、既存のリソースはそのまま動かし続けることができます。

ただし、`cdk import` ではリソースを新しく作ることはできません。

そのため、`grantRead` などで CDK が新しく追加する IAM ポリシーのようなリソースは、取り込みが終わった後に `cdk deploy` で作成しました。

### スタックを分ける

ベストプラクティスでは、ステートフルなリソースをステートレスなリソースとは別のスタックに置き、終了保護を有効にすることが推奨されています。

```ts
const app = new cdk.App()

// データを持つリソース（削除されると困るので終了保護を有効にする）
const statefulStack = new StatefulStack(app, 'StatefulStack', {
  terminationProtection: true,
})

// データを持たないリソース
new StatelessStack(app, 'StatelessStack', {
  bucket: statefulStack.bucket,
})
```

こうしておくことで、データを持つリソースのスタックを、スタックごと誤って削除してしまう事故を防ぐことができます。

### CDK のコードも AI に書いてもらう

既存のリソースと同じ設定の CDK のコードを、ゼロから手で書くのはかなり大変です。

そこで、既存のリソースの調査から CDK のコードを書く作業まで、Claude Code に手伝ってもらいました。

調査とコードの作成は AI、確認と実行は私、という役割分担にしました。

進め方は以下の通りです。

1. 読み取り専用の権限を付与したプロファイルで、AWS にログインする
2. Claude Code に AWS CLI で既存のリソースの設定を調べてもらう
3. 調べた設定をもとに、L2 Construct を使った CDK のコードを書いてもらう
4. 書かれたコードを私が確認し、マネコンの設定と突き合わせる
5. 読み取り専用のプロファイルからログアウトする
6. 書き込み権限のあるプロファイルに切り替え、`cdk diff` で差分を確認したうえで、`cdk import` を私が実行する
7. 取り込めなかった新しいリソースを、`cdk deploy` で私が作成する

### AI に AWS を調べさせるときの権限

AWS へのログインには、IAM Identity Center（SSO）を使いました。

読み取り専用の権限セットを用意しておき、そのプロファイルでログインします。

```bash
# 読み取り専用のプロファイルでログイン（プロファイル名は例）
aws sso login --profile my-app-readonly
```

権限セットには、AWS 管理ポリシーの `ReadOnlyAccess` を割り当てています。

似た名前の `ViewOnlyAccess` という管理ポリシーもありますが、こちらは S3 バケットの暗号化設定や IAM ポリシーの中身などが読めないため、今回のような調査には向いていません。

ただし、`ReadOnlyAccess` はリソースの設定だけでなく、S3 に保存したファイルやログの中身、ECS のタスク定義に平文で書いた環境変数なども読めてしまいます。

AI が調べた内容は AI のモデルに送られるため、機密情報を含むデータがある場合は、こうした操作を除外したカスタムポリシーを使うと、より安全だと思います。

また、SSO で発行される認証情報は一時的なものなので、期限のないアクセスキーを PC に置いておく必要もありません。

### Claude Code への指示

ログインできたら、Claude Code に調査と CDK のコードの作成を依頼します。

例えば、S3 バケットの場合は以下のように指示します。

```
AWS CLI のプロファイル my-app-readonly を使って、既存の S3 バケット example-upload-bucket の設定を調べてください。

調べた設定をもとに、以下の条件で CDK のコードを書いてください。

- L2 Construct を使う
- 暗号化、パブリックアクセスブロック、ライフサイクルルール、バケットポリシーなど、既存の設定と完全に一致させる
- データを持つリソースなので StatefulStack に追加し、removalPolicy は RETAIN にする
- cdk import や cdk deploy は実行しない
- CDK で再現できない設定や、判断に迷った設定があれば、最後にまとめて教えてください
```

他のリソースも、同じような形で指示します。

手作業で作った構成には、一般的なパターンから外れた設定が含まれていることもあります。

最後に「判断に迷った設定があれば教えてください」と入れておくと、AI がそういった設定をよくある書き方で勝手に置き換えてしまうのを防ぎやすくなります。

それでも念のため、AI が書いたコードは私が確認し、既存の設定が置き換えられていないかをチェックしました。

調査とコードの作成が終わったら、読み取り専用のプロファイルからはログアウトしておきます。

```bash
aws sso logout
```

この後の `cdk import` や `cdk deploy` は、読み取り専用のプロファイルでは実行できないため、書き込み権限のある別のプロファイルで私が実行します。

また、CDK を初めて使う AWS アカウントやリージョンでは、事前に `cdk bootstrap` を実行しておく必要があります。

### `cdk import` の手順

S3 バケットを例に、`cdk import` の流れをご紹介します。

先ほどの指示で、Claude Code が書いたコードは以下のようになりました（一部抜粋）。

```ts
export class StatefulStack extends Stack {
  public readonly bucket: s3.IBucket

  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props)

    this.bucket = new s3.Bucket(this, 'UploadBucket', {
      bucketName: 'example-upload-bucket', // 既存のバケット名
      encryption: s3.BucketEncryption.S3_MANAGED,
      blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
      removalPolicy: RemovalPolicy.RETAIN, // スタックを消してもバケットは残す
      // ライフサイクルルールなどは省略
    })
  }
}
```

ここで設定が既存のリソースとずれていると、次回のデプロイで意図しない変更が入ってしまいます。

暗号化やライフサイクルルール、バケットポリシーなど、Claude Code が AWS CLI で調べた設定を、マネコンとも 1 つずつ突き合わせて確認しました。

コードを確認できたら、`cdk diff` を実行し、取り込むリソースの追加以外に差分がないことを確認します。

`cdk import` では、取り込むリソースの追加以外の変更が許されていないためです。

```bash
npx cdk diff StatefulStack
```

問題がなければ、`cdk import` を実行します。

```bash
npx cdk import StatefulStack
```

今回はコードでバケット名を指定しているので、そのバケットがそのまま取り込まれます。

コードで名前を指定していないリソースの場合は、実際の名前を聞かれるので、既存のリソースの名前を入力します。

`cdk import` は、書いた設定が既存のリソースと一致しているかまではチェックしてくれません。

そのため、取り込んだ後に CloudFormation のドリフト検出を実行し、コードと実際のリソースの設定に差分がないかを確認しておくことをおすすめします。

ドリフト検出は、`cdk drift` コマンドで実行できます。

```bash
npx cdk drift StatefulStack
```

差分があるリソースがあれば、どのプロパティがずれているかが表示されます。

最後に、`cdk import` で取り込めなかった新しいリソースを、`cdk deploy` で作成します。

`StatefulStack` の場合は、`StatelessStack` から参照するための Export がここで作成されます。

`cdk deploy` の前にも `cdk diff` を実行し、新しいリソースの追加だけになっていることを確認しておきます。

```bash
npx cdk deploy StatefulStack
```

その後、`StatelessStack` でも同じように `cdk import` と `cdk deploy` を実行します。

`StatelessStack` で `grantRead` を使っている場合は、タスクロールに付ける IAM ポリシーが `cdk deploy` の時点で作成されます。

この流れを、スタックごとに繰り返してすべてのリソースを取り込みました。

### 注意したポイント

他にも、ベストプラクティスを参考に、以下の点に注意しました。

- **ステートフルなリソースの論理 ID を変えない**
  - リファクタリングなどで論理 ID が変わると、リソースが作り直されてしまいます
- **削除ポリシーを明示する**
  - データを持つリソースには `RemovalPolicy.RETAIN` を指定し、スタックから外れてもリソースが残るようにしました
- **L2 Construct が裏で作るリソースに注意する**
  - セキュリティグループやポリシーなどが自動で作られることがあるため、取り込む前に `cdk diff` で確認しました
- **依存関係のあるリソースは正しい順番で取り込む**
  - 依存関係のあるリソースは、まとめて取り込むか、依存される側から順に取り込む必要があります。そうしないと、参照先が見つからずに失敗します
  - スタックをまたいで参照している場合は、参照される側のスタックで `cdk import` と `cdk deploy` まで終わらせてから、参照する側のスタックを取り込みます。スタック間の参照に必要な Export は、`cdk deploy` の時点で作られるためです

また、CloudFormation の import では、取り込むリソースに `DeletionPolicy` が設定されている必要があります。

`DeletionPolicy` とは、スタックからリソースが外れたときや、スタックが削除されたときに、実際のリソースを削除するか（`Delete`）、残すか（`Retain`）、スナップショットを取ってから削除するか（`Snapshot`）を指定する CloudFormation の設定です。

CDK では、`removalPolicy` というプロパティが、この `DeletionPolicy` に対応しています。

`cdk import` を実行する前に、`cdk synth` で生成されたテンプレートを確認し、`DeletionPolicy` が付いていないリソースがあれば、CDK のコードで `removalPolicy` を指定しておきます。

```ts
new s3.Bucket(this, 'UploadBucket', {
  // ...
  removalPolicy: RemovalPolicy.RETAIN, // テンプレートでは DeletionPolicy: Retain になる
})
```

## CDK 化して AI が書くコードはどう変わったか

CDK 化の前後で、Claude Code に同じ機能の追加を頼んだときの結果を比べてみます。

### 例① S3 にファイルを保存する機能

> 集計結果を CSV にして、S3 に保存する機能を追加して

**CDK 化前**

```
CSV を生成して S3 にアップロードする処理を追加しました。

- 保存先のバケット名は環境変数 S3_BUCKET_NAME から取得します
- 環境変数 S3_BUCKET_NAME を設定してください
```

コード自体は正しく動きそうに見えますが、実際には以下の問題がありました。

- バケット名を渡している環境変数の名前が、実際のタスクの設定と違う
- タスクロールに、そのバケットへの書き込み権限がない

どちらも、デプロイして動かしてみるまで気づけませんでした。

**CDK 化後**

```
CSV を生成して S3 にアップロードする処理を追加しました。

- 保存先は StatefulStack の UploadBucket を使います
- バケット名は、StatelessStack でタスクに渡している環境変数 UPLOAD_BUCKET_NAME から取得します

なお、現在タスクロールには bucket.grantRead() で読み取り権限だけが付与されているため、
このままではアップロード時に AccessDenied になります。
StatelessStack に、書き込み権限を付与する grantPut を追加しました。
```

CDK のコードを読んで、実際の環境変数名を使ってくれたうえで、足りない権限の追加も一緒に行ってくれるようになりました。

### 例② 外部サービスへの通知機能

> 集計が終わったら Slack に通知する機能を追加して

**CDK 化前**

```
集計完了時に Slack へ通知する処理を追加しました。

- Webhook URL は環境変数 SLACK_WEBHOOK_URL から取得します
- 環境変数 SLACK_WEBHOOK_URL を設定してください
```

「環境変数を設定してください」で終わってしまい、どこにどう設定すればいいかは自分で調べる必要がありました。

**CDK 化後**

```
集計完了時に Slack へ通知する処理を追加しました。

- Webhook URL は環境変数 SLACK_WEBHOOK_URL から取得します
- 既存のタスクでは、機密情報を Secrets Manager から secrets として渡しているため、
  同じ方法で StatelessStack のタスク定義に SLACK_WEBHOOK_URL を追加しました

デプロイ前に、Secrets Manager に Webhook URL を登録してください。
```

既存の環境変数の渡し方に合わせて、アプリとインフラの両方を変更してくれるようになりました。

インフラの変更もアプリと同じくプルリクエストで確認できるので、AI に任せやすくなったと感じています。

また、私は `CLAUDE.md` に CDK のスタック構成や依存関係も書いておきました。
