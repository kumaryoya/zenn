## はじめに

https://zenn.dev/linkedge/articles/e281674de04c97

## active_record_doctor とは

active_record_doctor とは、Rails アプリのデータベーススキーマとモデルの定義を突き合わせて、設計上の不備を検出してくれる gem です。

「インデックスが張られていない外部キー」や「uniqueness バリデーションがあるのに DB 側にユニークインデックスがない」といった、動作はするけれど問題を抱えている箇所を指摘してくれます。

RuboCop がコードの書き方をチェックする gem だとすれば、active_record_doctor は**データベース周りの設計をチェックする gem** というイメージです。

検出項目は「検出器（detector）」という単位で分かれており、2.0.1 では次の15種類が用意されています。

| 検出器 | 検出内容 |
| --- | --- |
| `extraneous_indexes` | 他のインデックスで代替できる不要なインデックス |
| `missing_foreign_keys` | 外部キー制約が張られていない外部キーらしきカラム |
| `unindexed_foreign_keys` | インデックスが張られていない外部キー |
| `missing_unique_indexes` | uniqueness バリデーションに対応する DB 制約がない |
| `missing_non_null_constraint` | 常に presence 検証されるのに NOT NULL 制約がない |
| `missing_presence_validation` | NOT NULL なのに presence バリデーションがない |
| `incorrect_boolean_presence_validation` | boolean カラムへの presence バリデーション |
| `incorrect_length_validation` | DB の桁数制限と length バリデーションの不一致 |
| `incorrect_dependent_option` | 不適切な `dependent` オプション |
| `mismatched_foreign_key_type` | 外部キーと参照先で型が異なる |
| `short_primary_key_type` | 主キーの整数型が小さい |
| `table_without_primary_key` | 主キーがないテーブル |
| `table_without_timestamps` | `created_at` / `updated_at` がないテーブル |
| `undefined_table_references` | 存在しないテーブル・ビューを参照しているモデル |
| `unindexed_deleted_at` | 論理削除カラムを考慮していないインデックス |

## 導入方法

Gemfile に追加します。

開発時にしか使わないので、development と test のグループに入れます。

```diff ruby:Gemfile
+ gem 'active_record_doctor', group: [:development, :test]
```

```bash
docker compose exec app bundle install
```

インストールすると rake タスクが追加されます。

```bash
docker compose exec app bundle exec rake -T | grep active_record_doctor
rake active_record_doctor                                             # Run all active_record_doctor detectors
rake active_record_doctor:extraneous_indexes                          # identify indexes that can be dropped without degrading performance
rake active_record_doctor:extraneous_indexes:help                     # Show help for extraneous_indexes
~ (省略) ~
rake active_record_doctor:unindexed_foreign_keys                      # detect unindexed foreign keys
rake active_record_doctor:unindexed_foreign_keys:help                 # Show help for unindexed_foreign_keys
```

検出器ごとに実行用のタスクと `:help` タスクが用意されています。

## いきなり躓いた話

さっそく全検出器を実行してみます。

```bash
docker compose exec app bundle exec rake active_record_doctor
rake aborted!
Zeitwerk::NameError: expected file /template_app/app/graphql/test_app_schema.rb to define constant TestAppSchema, but didn't (Zeitwerk::NameError)
```

データベースの指摘が出る前に、まったく別のエラーで落ちてしまいました。

原因は、`test_app_schema.rb` というファイル名なのに、中で定義しているクラスが `TemplateAppSchema` になっていたことでした。

過去にアプリ名を変更した際、ファイル名を直し忘れていたようです。

:::message
active_record_doctor は、モデルの定義を読み取るために実行前に `Rails.application.eager_load!` を呼びます。

development 環境では通常 eager load されないため、こうしたファイル名とクラス名の不一致に気付けません。

本番環境では eager load されるので、**デプロイして初めて発覚するタイプの不具合**です。
:::

ファイル名を `template_app_schema.rb` に変更したところ、無事に実行できるようになりました。

なお、同種の不一致は次のコマンドでまとめて確認できます。

```bash
docker compose exec app bundle exec rails zeitwerk:check
```

データベースの検査をしにきたはずが、先に別の問題が見つかるという思わぬ副産物でした。

## 修正①：ユニークインデックスの欠落

まずはこの指摘です。

```
add a unique index on chain_words(word) - validating uniqueness in ChainWord without an index can lead to duplicates
```

`ChainWord` モデルには `validates :word, uniqueness: true` が書かれているものの、DB 側にユニークインデックスがない、という指摘です。

これは「動いているから問題ない」と見過ごされがちですが、実害があります。

Rails の uniqueness バリデーションは、**保存前に SELECT で重複を確認しているだけ**です。

同じ値を持つリクエストがほぼ同時に来ると、どちらも「重複なし」と判定されてしまい、結果として重複データが登録されます。

これを確実に防げるのは DB のユニークインデックスだけです。

マイグレーションを作成します。

```bash
docker compose exec app bundle exec rails g migration AddUniqueIndexToChainWordsWord
```

```ruby:db/migrate/20260822112734_add_unique_index_to_chain_words_word.rb
class AddUniqueIndexToChainWordsWord < ActiveRecord::Migration[7.0]
  def change
    add_index :chain_words, :word, unique: true
  end
end
```

```bash
docker compose exec app bundle exec rails db:migrate
== 20260822112734 AddUniqueIndexToChainWordsWord: migrating ===================
-- add_index(:chain_words, :word, {:unique=>true})
   -> 0.0057s
== 20260822112734 AddUniqueIndexToChainWordsWord: migrated (0.0057s) ==========
```

再度検出器を実行します。

```bash
docker compose exec app bundle exec rake active_record_doctor:missing_unique_indexes
```

出力がなくなり、指摘が解消されたことが確認できました。

:::message
すでに重複データが存在する場合、ユニークインデックスの作成は `Duplicate entry` で失敗します。

その場合は、先に重複データを整理する必要があります。

```bash
docker compose exec app bundle exec rails runner 'p ChainWord.group(:word).having("count(*) > 1").count'
```
:::

## 修正②：不要なインデックス

続いてこの指摘です。

```
remove the index index_daily_prices_on_stock_id from the table daily_prices - queries should be able to use the following index instead: index_daily_prices_on_stock_id_and_date
```

`daily_prices` テーブルには `stock_id` 単体のインデックスと、`stock_id` と `date` の複合インデックスの両方が張られていました。

MySQL の複合インデックスは**左端のカラムから順に部分的に使える**ため、`(stock_id, date)` のインデックスは `stock_id` だけの検索にもそのまま使えます。

つまり `stock_id` 単体のインデックスは完全に無駄になっており、検索性能を落とさずに削除できます。

インデックスは検索を速くする一方で、レコードの登録・更新のたびに更新コストがかかり、ストレージも消費します。

冒頭で触れた RDS の I/O の話とも繋がりますが、**使われないインデックスは書き込み性能とストレージを削るだけの存在**です。

マイグレーションを作成します。

```bash
docker compose exec app bundle exec rails g migration RemoveExtraneousIndexFromDailyPrices
```

```ruby:db/migrate/20260822112856_remove_extraneous_index_from_daily_prices.rb
class RemoveExtraneousIndexFromDailyPrices < ActiveRecord::Migration[7.0]
  def change
    remove_index :daily_prices, :stock_id
  end
end
```

```bash
docker compose exec app bundle exec rails db:migrate
== 20260822112856 RemoveExtraneousIndexFromDailyPrices: migrating =============
-- remove_index(:daily_prices, :stock_id)
   -> 0.0049s
== 20260822112856 RemoveExtraneousIndexFromDailyPrices: migrated (0.0049s) ====
```

こちらも指摘が解消されました。

## 誤検知との付き合い方

31件のうち、対応すべきでないものも含まれていました。

### 存在しないテーブルへの参照

```
ActiveStorage::Blob references a non-existent table or view named active_storage_blobs
```

これは Active Storage や Action Text のモデルが Rails 本体に定義されている一方で、対応するマイグレーションを導入していないために出ている指摘です。

自分のアプリの問題ではないため、除外してしまって構いません。

### MySQL 特有の大量検出

今回もっとも件数が多かったのが `incorrect_length_validation` の17件です。

```
the schema limits stocks.market_name to 255 characters but there's no length validator on Stock.market_name - remove the database limit or add the validator
```

これは「DB 側に255文字の制限があるのに、モデル側に length バリデーションがない」という指摘です。

MySQL では `t.string` が `varchar(255)` になるため、**文字列カラムを持つモデルのほぼすべてで発生します**。

一方で、PostgreSQL の `t.string` は桁数制限なしの `character varying` になるため、ここまで大量には出ません。

MySQL を使っている場合、この検出器はノイズになりやすい点は知っておくとよさそうです。

ただし、17件のうち1件だけは毛色が違いました。

```
the schema limits articles.body to 255 characters but the length validator on Article.body enforces a maximum of 65535 characters - set both limits to the same value or remove both
```

モデルは65535文字まで許可しているのに、DB は255文字までしか保存できないという指摘です。

これはバリデーションを通過してもデータベースへの保存で失敗する、**明確な不整合**です。

ノイズが多い検出器の中にも本物の不具合が紛れているので、件数だけ見て切り捨てないよう注意が必要です。

### 設定ファイルで除外する

除外はプロジェクトルートに `.active_record_doctor.rb` を置いて設定します。

```ruby:.active_record_doctor.rb
ActiveRecordDoctor.configure do
  # Rails 標準機能のモデルは、マイグレーションを導入していないため除外する
  detector :undefined_table_references,
    ignore_models: [
      "ActionMailbox::InboundEmail",
      "ActionText::RichText",
      "ActionText::EncryptedRichText",
      "ActiveStorage::Attachment",
      "ActiveStorage::Blob",
      "ActiveStorage::VariantRecord"
    ]

  # カラム単位でも除外できる
  detector :incorrect_length_validation,
    ignore_attributes: [
      "Stock.code",
      "Stock.name"
    ]
end
```

`ignore_models` はモデル単位、`ignore_attributes` はカラム単位での除外です。

どのオプションが使えるかは検出器ごとに異なり、`:help` タスクで確認できます。

```bash
docker compose exec app bundle exec rake active_record_doctor:missing_unique_indexes:help
missing_unique_indexes - detect uniqueness validators not backed by a database constraint

Configuration options:
  - ignore_models (local and global) - models whose uniqueness validators should not be checked
  - ignore_columns (local only) - specific validators, written as Model(column1, column2, ...), that should not be checked
  - ignore_join_tables (local only) - join tables that should not be checked for existence of unique indexes
  - enabled (local only) - set to false to disable the detector altogether
```

`local and global` と書かれているオプションは、`global :ignore_models, [...]` の形式ですべての検出器にまとめて適用することもできます。

| `undefined_table_references` | 6 | 0 |
| `incorrect_dependent_option` | 3 | 3 |
| `missing_presence_validation` | 3 | 3 |
| `extraneous_indexes` | 1 | 0 |

いきなりゼロを目指すのではなく、**実害の大きい検出器から潰していくのが現実的**だと感じました。

## CI に組み込む

ここまでは手元で実行してきましたが、テーブルを追加するたびに手で叩くのは現実的ではありません。

active_record_doctor は**指摘が1件でもあると終了ステータス 1 を返す**ため、CI に組み込むのに向いています。

実際に確認してみます。

```bash
docker compose exec app bundle exec rake active_record_doctor > /dev/null; echo $?
1
```

### database.yml を環境変数に対応させる

CI では MySQL のホスト名が開発環境と異なるため、`database.yml` を環境変数で上書きできるようにしておきます。

```diff yaml:config/database.yml
  default: &default
    adapter: mysql2
    encoding: utf8mb4
    pool: <%= ENV.fetch("RAILS_MAX_THREADS") { 5 } %>
    username: user
    password: password
-   host: db
+   host: <%= ENV.fetch("DATABASE_HOST") { "db" } %>
    port: 3306
```

### ワークフローを作成する

GitHub Actions のワークフローを作成します。

```yaml:.github/workflows/active_record_doctor.yml
name: active_record_doctor

on:
  pull_request:

jobs:
  active_record_doctor:
    runs-on: ubuntu-latest

    services:
      mysql:
        image: mysql:8.4.7
        env:
          MYSQL_ROOT_PASSWORD: password
          MYSQL_DATABASE: template_app_test
          MYSQL_USER: user
          MYSQL_PASSWORD: password
        ports:
          - 3306:3306
        options: >-
          --health-cmd="mysqladmin ping -h 127.0.0.1"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=5

    env:
      RAILS_ENV: test
      DATABASE_HOST: 127.0.0.1

    steps:
      - uses: actions/checkout@v4

      - uses: ruby/setup-ruby@v1
        with:
          ruby-version: 3.3.5
          bundler-cache: true

      - name: Set up database
        run: bundle exec rails db:schema:load

      - name: Run active_record_doctor
        run: bundle exec rake active_record_doctor
```

active_record_doctor が見ているのはスキーマとモデルの定義だけなので、`db:schema:load` を実行すれば検査できます。

テストデータの投入もテストの実行も不要なので、CI としては軽量です。

### 段階的に導入する

ただし、今回のように指摘が21件残った状態でそのまま組み込むと、**すべての Pull Request が落ち続けます**。

現実的には、次のどちらかから始めるのがよさそうです。

ひとつは、`.active_record_doctor.rb` で既存の指摘をすべて除外して、いったんゼロの状態を作る方法です。

新しく追加したテーブルやモデルの問題だけが検出されるようになるので、これ以上悪化させないという運用ができます。

もうひとつは、実害の大きい検出器だけを CI で実行する方法です。

```yaml
      - name: Run active_record_doctor
        run: |
          bundle exec rake active_record_doctor:missing_unique_indexes
          bundle exec rake active_record_doctor:extraneous_indexes
          bundle exec rake active_record_doctor:unindexed_foreign_keys
```

まずは狭い範囲で導入して、対応が進むにつれて検出器を増やしていくのが無理のない進め方だと思います。

## おわりに

今回は、active_record_doctor を使ってデータベース設計の不備を検出してみました。

導入は Gemfile に1行追加するだけで、実行も rake タスク1つと非常に手軽です。

そのうえで、ユニークインデックスの欠落や不要なインデックスといった、目視ではまず気付けない問題を洗い出してくれました。

終了ステータスで結果が分かるため、Brakeman や bundler-audit と同じように CI に組み込んで運用できるのも嬉しいポイントです。
